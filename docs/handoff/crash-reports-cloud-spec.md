# Client crash and error reports to the Roastlocal cloud: what the cloud needs to provide

From: RoastArtisan client chat · To: Roastlocal cloud master chat · Date: 2026-10-23
Status: proposal. Nothing is implemented on either side yet. The client work starts once the endpoint below
exists (or once you agree a different contract with the owner).

## Why

RoastArtisan (the desktop roasting client, a PyQt6 fork of Artisan, used by every roaster on the cloud) has no
way to tell us that it crashed or hit an error. Today:

- an unhandled exception shows a dialog on the roaster's screen. Since 1.0.14 it says "report to Roastlocal
  support", and that only helps if the roaster actually writes to us;
- the "send log" function of upstream Artisan, which mailed logs to the Artisan team, is disabled (owner
  decision, 1.0.13);
- the log file stays on the roaster's machine (`roastartisan.log`, rotating, 3 × 800 KB).

So we learn about client bugs only when a roaster complains, usually without the traceback. The goal is for the
client to send a crash or error report to the cloud automatically, so the owner can see what broke, for whom,
in which version and how often.

## What the client will send

Two kinds of reports:

1. **crash**: an unhandled Python exception, caught by the global `sys.excepthook`, which today shows the
   dialog. Always sent.
2. **error**: errors the app already records in its error log (`adderror()`: device or serial failures,
   IO errors, failed exports). These are noisier. They are deduplicated and rate-limited on the client
   (see below), and the owner may decide to switch them off.

### Endpoint (proposed)

```
POST {api_base_url}/client/reports          # api_base_url = https://roastlocal.ru/api/v1
Content-Type: application/json
Content-Encoding: gzip                      # the client gzips every body it sends (existing behaviour)
Authorization: Bearer <session token>       # ONLY if the roaster is logged in, see "Authentication"
User-Agent: Artisan/<version> (<os>; <os_version>; <arch>)   # existing client header
Accept-Language: ru                         # existing client header
```

Response: `202 Accepted` with `{"id": "<report id>"}`. Anything else (4xx/5xx/no response) means "not stored".
The client then keeps the report locally and retries later.

### Payload (JSON)

```jsonc
{
  "schema": 1,
  "kind": "crash",                       // "crash" | "error"
  "client_report_id": "uuid4",           // generated by the client; resends of the same report reuse it -> idempotency key
  "occurred_at": "2026-10-23T15:59:12.345Z",   // UTC ISO-8601, when it happened (not when it was sent)
  "fingerprint": "sha1 hex",             // client-computed: exception type + top 5 frames (file:function), no line numbers
                                         // -> lets the cloud group identical crashes across versions

  "app": {
    "version": "1.0.14",                 // artisanlib.__version__
    "revision": "a1b2c3d",               // git short hash stamped by CI
    "build": "0",
    "frozen": true                       // packaged app (true) vs run from source (false)
  },
  "platform": {
    "os": "Darwin",                      // Darwin | Windows | Linux
    "os_version": "14.6.1",
    "arch": "arm64",
    "python": "3.13.12",
    "qt": "6.10.2",
    "locale": "ru"
  },
  "context": {                           // what the roaster was doing; all optional
    "machine": "Probat P12III",          // configured roaster machine/preset name
    "device": "Phidget 1048",            // main temperature device type
    "sampling": true,                    // was a roast being recorded
    "roast_phase": "after FCs",          // coarse phase if sampling
    "ui_mode": "production"
  },
  "account": {                           // present only if logged in; the cloud can take these from the token instead
    "account_id": "…",                   // plus_account_id
    "operator": "…"                      // current operator nickname (multi-operator login)
  },

  "error": {
    "type": "ZeroDivisionError",
    "message": "float division by zero", // scrubbed (see Privacy)
    "traceback": "Traceback (most recent call last): …",   // full text, scrubbed, max 64 KB
    "line": "canvas.py:9545"
  },
  "log_tail": "…last ~300 lines of roastartisan.log…",    // scrubbed, max 128 KB
  "occurrences": 1                       // for kind=error: how many identical errors were folded into this report
}
```

Size: the whole body is under **256 KB uncompressed**, and the client truncates `traceback` and `log_tail` to stay
under that. Please reject anything above 1 MB with 413.

### Authentication

Crashes also happen **before login** or after the session expired, and those are often the interesting ones
(startup crashes, login bugs). So:

- **Logged in**: the client sends the normal `Authorization: Bearer` token, and the cloud links the report to the
  account and operator.
- **Not logged in**: the client sends no token. The cloud should still accept the report anonymously, rate-limited
  per IP (suggested: 30 reports/hour/IP, 429 above), with `account` empty.

If you'd rather not have an open unauthenticated endpoint, the fallback is that the client queues pre-login
reports and sends them after the next successful login. Tell us which you prefer.

### Client behaviour (for your information; implemented on the client side)

- A report goes into a small local outbox (separate from the roast outbox) and is sent in the background, never
  blocking the UI or a running roast. It is retried until it gets `202`, like roast data, and the same
  `client_report_id` is reused, so **the endpoint must be idempotent on `client_report_id`**: a repeat returns
  202 with the existing id.
- Dedup and rate limit on the client: an identical `fingerprint` is sent at most once per hour (with
  `occurrences`), and at most 20 reports per day per installation.
- Settings switch "Send error reports to Roastlocal" (Config menu), on by default. The crash dialog says that
  a report was sent.

## Privacy (please confirm)

The client scrubs before sending:

- the session token, passwords, and anything after `Bearer `; e-mail addresses are replaced by `<email>`;
- the user's home directory path is replaced by `~`;
- profile contents (roast data) are **not** attached; only file names can appear in the traceback or log.

Not scrubbed: machine/device names, roast titles and bean names that appear in log lines, and the IP address
(the cloud sees it anyway). If that is not acceptable for your privacy policy or terms, tell us what else to cut.

## What the cloud side needs (suggested scope)

1. **Store** the reports: a `client_reports` table with the fields above, plus `received_at`, `ip`, and
   `account_id` from the token if present. Unique on `client_report_id`.
2. **Group** by `fingerprint`: first and last seen, count, affected versions, affected accounts.
3. **View** for the owner (admin only): a list of groups, newest first, filterable by version, kind and account;
   the report detail shows the traceback and log tail.
4. **Notify** the owner when a new fingerprint appears, or when a group spikes after a release (for example
   by Telegram or e-mail, whatever the cloud already uses).
5. **Retention**: suggested 90 days for reports, groups kept.

Out of scope for now: symbolication, attachments, replying to the roaster from the cloud.
